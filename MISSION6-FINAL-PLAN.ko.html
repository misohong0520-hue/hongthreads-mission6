미션 6 — H DRT 개발판

원본 DRT의 화면·메뉴·폼·팝업·사용 흐름을 유지한다. Supabase 저장·파일 처리와 Vertex WIF는 기존 화면 뒤에서 연결하고, 검증 후 승인받아 AWS에 배포한다.

대상: 현재 drt-agczero-insights-local 개발판. 실제 진행·검증 상태는 구현 보고서에서 확인한다. 현재는 원본 UI 일치 수정과 재검증을 진행 중이며, 배포는 계속 승인 후에만 한다.

확정 사항구조데이터와 기능CRUD·파일공개·세션구현·배포검증·제출

1. 확정 사항과 현재 기준선

항목확정 내용
서비스 대상현재 DRT 로컬 개발판을 원본과 동일한 화면으로 구현한다. 원본 13개 화면, 메뉴, 편집기, 폼, 팝업, 프롬프트·결과 선택·저장·재열기 흐름을 유지한다. 별도 자료 관리 대시보드나 새 메뉴·연결 안내를 붙이지 않는다.
저장소Supabase를 벤치마킹 한 기능에만 한정하지 않는다. 모든 기능의 영속 데이터·첨부파일·작업 이력·동기화 상태에 적용한다. 외부 서비스의 실제 업무 처리는 해당 API를 계속 이용한다.
공개 범위모든 화면은 공개한다. 원본 계정은 방문자마다 각자 연결한다. 현재 사용자의 세션을 공용 세션으로 배포하지 않는다.
기존 연결현재 소유자의 원본 세션과 연결된 쿠팡 파트너스를 유지한다. AI는 현재 EC2의 Vertex AI WIF와 gemini-3.8-flash를 사용한다.
제휴 기능현재 계정에 보이는 쿠팡·토스·브랜드커넥트를 기준으로 검증한다. 워드로브는 원본의 제한된 표시 조건을 유지하며, 일반 사용 기능의 미해결 오류로 계산하지 않는다.
브랜딩제공된 초록색 H 로고를 사용한다. 사이드바 하단의 프로필 이름·아바타 표시를 제거하고 마이페이지·로그아웃 기능은 유지한다.
배포Vercel 대신 기존 wordpress-hongsik-blog EC2, i-0e587c84b3642e794, 3.35.8.24를 사용한다. 기존 WordPress와 Vertex worker는 계속 운영한다.

이전 검증 기록: 원본 화면 13개, 메뉴 이동 12개, 화면 조작 19개를 확인했고 기존 오류 5개를 수정했다. 이후 저장·세션·확장·WIF를 포함한 자동 검사 100개와 실제 Supabase CRUD·파일·AI 검증을 통과했다. 이 결과는 원본 UI 일치 수정 전의 기준선이며 현재 수정본의 재검증 결과를 대신하지 않는다.

현재 수정: 독립적으로 추가했던 /workspace 자료 관리 화면과 원본에 주입한 메뉴·연결 안내를 제거했다. Supabase Database·Storage, 사용자별 세션, 원본 API 동기화, 클라우드 확장과 Linux WIF 어댑터는 유지한다. 요청받은 H 로고와 하단 이름·아바타 미표시도 유지했다. 원본 화면에서 실제 등록·본문·파일·작성 기준 수정·폴더 생성/수정/삭제·자료 및 첨부 삭제를 검증했다. 최초 HTTPS 배포본은 존재하며 이후 수정본은 승인 전까지 서버에 반영하지 않는다.

최신 사용자 지시 반영: 제품 화면은 원본과 같아야 한다. 미션 6 시연도 기존 벤치마킹·원고·페르소나 등의 화면에서 진행한다. 별도 대시보드·관리 메뉴를 추가하던 이전 시연 방식은 사용하지 않는다. 세션 설정은 기존 개발용 /__live/ 화면으로 분리하고 제품 화면에 새 안내를 주입하지 않는다.

추가 로컬 점검: 3종 병렬 생성의 429 거절, 원고·세션·양식의 ID 해석, 일괄 삭제·작업/제휴 링크 분류, 이전 세션 중복 사본, 사용법 iframe 차단을 수정했다. 자동 검사110개, 실제 WIF 동시 생성3건·작은 영상 분석, 실제 세션 사본 정리를 확인했다. 제품 UI와 배포 승인 조건은 유지한다.

원본 배포 JavaScript와 API 응답을 확보한 상태이며, 원본 서버 소스·DB·서비스 권한을 복제한 상태는 아니다. 네트워크 응답은 요청·응답 계약을 확인하는 근거로 사용한다. 파싱만으로 Threads 게시 서버, 상품 공급 API 또는 원본 권한을 독립 재구현할 수 있다고 가정하지 않는다.

2. 구현 구조

공개 브라우저→Nginx · HTTPS→Next.js + DRT 연결 서버→Supabase / 원본 API / Vertex WIF

원본 UI와 Next.js 서버 구성

  • 기존 프로젝트 내부 web/에 Next.js 16.4.6 App Router·TypeScript 앱을 추가한다. 의존성은 lockfile로 고정하고, 프로젝트 전용 Node.js 24 실행 환경을 사용한다.
  • 검증된 원본 실행 자산과 현재 13개 페이지를 유지한다. 기본 화면은 /dashboard/insights이며 메뉴별 원래 주소를 사용한다. 추가됐던 /workspace HTML 주소는 해당 원본 화면으로 이동시킨다. 서버용 /workspace/api/ 계약은 호환을 위해 유지하며 제품 메뉴에 노출하지 않는다.
  • Next.js와 연결 서버는 공통 데이터 서비스, 입력 검증, 파일 처리와 원본 API 호환을 담당한다. 기존 화면의 API 경로·본문·응답 형식과 등록·상세·수정 방식은 유지한다. 원본 화면을 다른 디자인의 관리 화면이나 편집기로 바꾸지 않는다.
  • 미션 6의 등록 → 목록 → 상세 → 수정 → 삭제는 기존 벤치마킹 화면의 폼·카드·상세 팝업으로 시연한다. 원래 보관함·폴더·확장 수집 흐름을 사용하고 ‘자료 관리’ 같은 추가 진입점을 만들지 않는다. 같은 서버 저장 계층을 나머지 기존 기능에도 적용한다.
  • 현재 Windows 실행은 계속 지원한다. DATA_BACKEND=local|supabase, VERTEX_TRANSPORT=ssh|local로 저장소·실행 환경을 명시적으로 선택한다. AWS에서는 Supabase와 로컬 worker 호출만 사용한다.

서비스 역할과 내부 연결

Next.js는 127.0.0.1:9250, DRT 연결 서버는 127.0.0.1:9251에서 실행한다. 사용자에게는 9251의 원본 DRT 화면을 제공한다. 연결 서버가 사용자 세션·원본 API·WIF와 공통 Supabase 저장 계층을 관리하고 Next.js는 서버 구성과 호환 경로를 유지한다. 공개 Nginx에서 내부 경로를 차단하며 브라우저가 보낸 사용자 ID나 workspace ID를 신뢰하지 않는다.

원본 자산은 원본 보존본과 개발용 변경본을 분리하고 해시 검증을 유지한다. 원본 배포 버전 변경 시 새 자산을 수집·검증·패치·회귀 검사한 뒤 활성화한다. 미확인 새 파일을 자동 허용하거나 구버전 데이터로 오류를 감추지 않는다.

3. 전체 기능의 Supabase 적용

기능Supabase에 저장할 데이터실제 처리 및 보존 기준
인사이트·트렌드조회 스냅샷, 수집 시각, 필터, 검색 기록, API 상태현재 원본의 트렌드·인기 글 검색을 계속 호출한다. 최근 스냅샷과 실시간 결과를 구분한다.
일반·멀티·스마트 멀티 에디터원고, 타래, 입력 리소스, 생성 옵션, 편집 세션, 결과 선택, 자동 저장 상태기존 편집기와 프롬프트를 유지한다. 원고 생성은 WIF, 다시 열기는 실제 저장 데이터로 검증한다.
내 원고·게시물 보관함초안, 수정 이력, 첨부 관계, 상태, 원본 레코드 IDSupabase 작성 자료와 원본 게시물을 구분한다. 원본 게시물의 변경·삭제는 실제 원본 API 성공을 확인한다.
벤치마킹폴더, 스크랩, 원문·메모, 링크, 미디어, 정렬, 수집 작업현재 로컬 보관함은 Supabase로 이전한다. 확장 수집·수동 등록·새로고침을 유지한다. 원본 공용 보관함은 권한이 있을 때 원본 조회 경로를 사용한다.
페르소나·댓글 양식프로필, 프롬프트, 기본값, 양식, 계정별 연결 관계원본에 이미 있는 항목은 최초 연결 시 읽어 가져오고 원본 ID를 유지한다. 수정·삭제 시 원본 반영이 필요한 계약을 유지한다.
계정 인사이트·게시글·멘션조회 결과, 기간별 스냅샷, 분석 결과, 응답 시각계정별 실제 API를 사용한다. 기록이 없는 기간은 데이터 없음으로 표시하고 수치를 생성하지 않는다.
영상·이미지 아카이브Storage 파일, 미디어 메타데이터, 카테고리, 첨부 관계목록·선택·재생·다운로드·에디터 첨부·AI 분석을 연결한다. 기존 외부 영상은 출처 URL을 보존하며 무조건 재업로드하지 않는다.
쿠팡·토스·브랜드커넥트선택 상품, 출처·상품 ID, 링크 메타데이터, 작성 원고와의 관계상품 조회와 실제 제휴 링크 생성은 원본 연동 계약을 유지한다. 등록된 쿠팡 연결을 임의로 재설정하지 않는다.
수익 인증 라운지입력 내용, 증빙 파일, 원본 참조, 변경·공개 상태원본에 공개되는 등록·수정은 외부 응답 확인 후 반영하며 비공개 초안과 구분한다.
발행·예약·댓글 작업요청 이력, 원본 작업 ID, 상태, 결과, 실패 사유실제 처리는 원본 서비스에 위임한다. 동일 요청을 재시도할 때 중복 발행하지 않도록 작업 ID와 상태를 확인한다.
마이페이지·계정 연결사용자별 설정, 연결된 계정의 식별 참조·상태·확인 시각원본 세션·제휴 비밀키·Google 자격값은 업무 테이블에 저장하지 않는다. 구독·결제 상태는 원본 판정을 따른다.
AI 및 오류 이력사용자별 입력·출력·선택 결과, 모델, 작업 상태, 비밀값을 제거한 오류현재 Vertex 프로젝트·WIF·모델을 유지한다. 결과 형식은 원본 클라이언트가 처리하는 계약으로 반환한다.

데이터 모델과 정합성

  • 기본 테이블은 workspaces, app_sessions, accounts, drafts, editor_sessions, personas, comment_templates, scrap_folders, scraps, assets, insight_snapshots, affiliate_items, affiliate_links, publish_jobs, revenue_entries, generation_jobs, sync_events로 구성한다. 공개성이 확인된 공통 트렌드 캐시는 별도 테이블로 둔다.
  • 개인 자료는 UUID 기본키, 필수 workspace_id, 생성·수정 시각을 공통으로 가진다. 원본 ID는 별도 upstream_id로 유지한다. 폴더·스크랩·첨부 관계는 외래키로 연결하고, 표시·검색 필드는 타입이 있는 컬럼으로 관리한다. 복잡한 원본 콘텐츠 구조만 JSONB로 보존한다.
  • 신규 앱 자료와 기존 로컬 벤치마킹은 Supabase가 주 저장소다. 원본에 실재하는 원고·계정·게시물·설정은 해당 원본 ID를 보존하며, 원본 변경 요청 성공 뒤 Supabase에 반영한다. 원본이 관리하는 정보의 진실값을 DB 사본으로 덮어쓰지 않는다.
  • 외부 처리와 DB 저장은 단일 트랜잭션이 아니므로 동기화 상태를 별도 기록한다. 원본 성공·DB 실패는 ‘원본 반영 완료, 보관함 동기화 대기’로 처리해 원본 작업을 재실행하지 않는다. DB 작성 자료를 외부로 보낼 때는 작업 ID로 중복을 막고 원본 실패를 성공으로 표시하지 않는다.
  • 변경 요청에는 행 버전 또는 마지막 수정 시각을 사용한다. 오래 열린 화면의 덮어쓰기는 충돌 안내 후 새 데이터를 다시 읽는다. 일반 CRUD는 실제 DB에서 삭제하고, 원본이 제공하는 보관 처리와 외부 게시물 삭제는 각각의 의미를 유지한다.

4. 미션 6 CRUD·파일 구현 명세

대표 사용자 흐름

기존 벤치마킹 보관함 → 원래 등록·수집 방식으로 자료 저장 → 기존 카드·상세 팝업에서 첨부 확인 → 기존 수정 동작 → 새로고침 후 확인 → 기존 삭제 동작 → 목록과 저장소에서 삭제 확인. 원본 UI를 유지한 채 같은 저장 계층을 나머지 기능에도 적용한다.

화면·인터페이스구현 계약
목록/dashboard/benchmark의 원본 목록·검색·폴더·분류·페이지 방식을 유지한다. 기존 제어와 화면 구성을 바꾸지 않고 서버 저장소만 연결한다.
등록·상세·수정원본 벤치마킹의 등록·수집·상세 팝업·수정 동작을 유지한다. 별도 /workspace 편집 페이지는 사용하지 않는다. 없는 항목과 다른 사용자의 항목은 서버에서 404로 처리한다.
CRUD API/workspace/api/v1/benchmarks의 GET·POST, /workspace/api/v1/benchmarks/[id]의 GET·PATCH·DELETE. 폴더·원고·페르소나·양식·증빙도 같은 서비스 계층과 소유권 검사를 재사용한다.
입력원본 폼의 본문·작성자·작성 기준·폴더·첨부 입력을 유지하고 제목 입력란을 추가하지 않는다. 서버의 관리용 제목은 본문 등에서 도출한다. 수동 등록의 MANUAL_INPUT 표식을 호환 처리하며 본문·크기·형식·소유권을 서버에서도 검사한다.
응답·오류새 API는 데이터와 페이지 정보, 오류 코드·메시지·필드 오류를 구분한다. 400 입력 오류, 401 연결 필요, 404 없는 자료, 409 수정 충돌, 413 크기 초과를 처리한다. 기존 DRT API 응답 형태는 호환 계층에서 유지한다.
상태 표시원본의 조회·저장 로딩, 빈 목록, 필드 오류, 실패·완료·삭제 확인 표현을 사용한다. 저장 중 중복 클릭을 막고 실패 시 입력값을 유지하며 새 배너나 별도 관리 화면을 붙이지 않는다.

Supabase Storage

  • 비공개 drt-assets 버킷을 사용하고 경로는 workspace/entity/file-uuid.ext로 생성한다. 실제 MIME·파일 서명을 확인하며 이미지와 영상 형식은 기존 편집기 지원 범위를 따른다. 원본 제한에 맞춰 파일당 최대 50MB, 편집기 첨부는 최대 9개로 시작한다.
  • 파일은 서버에서 사용자·크기·형식을 확인한 뒤 서명된 업로드로 Storage에 전송하고, 완료 시 DB의 첨부 관계를 저장한다. 미완료 업로드는 임시 상태로 남겨 만료 정리하고, 레코드 저장 실패 시 파일이 정상 첨부된 것처럼 표시하지 않는다.
  • 미리보기·다운로드는 소유권 확인 후 단기 서명 URL을 발급한다. 파일 없는 상세, 깨진 파일, 업로드 취소·실패, 기존 파일 교체·삭제를 처리한다. 레코드 삭제 후 참조가 없는 파일은 정리 작업으로 제거하며 실패는 재시도 대상으로 남긴다.
  • Threads 발행용 미디어는 원본 업로드 계약에 맞게 전달하고 그 결과 URL을 사용한다. 미리보기용 단기 URL을 장시간 뒤의 예약 발행 URL로 재사용하지 않는다.

5. 전체 공개와 사용자별 원본 세션

  • 모든 원본 페이지는 연결 전에도 열린다. 연결 전 자료는 별도 guest workspace에 분리한다. 개인 원본 API가 필요한 기능은 실제 계정이나 성공 응답을 꾸며 넣지 않으며, 별도의 체험 대시보드·연결 배너를 추가하지 않는다.
  • 원본 연결 시 각 방문자가 기존 개발용 /__live/ 설정에서 자신의 세션을 제출하고 서버가 원본 세션 API로 확인한다. 제품 메뉴에는 새 연결 항목을 만들지 않는다. 검증된 원본 사용자 식별자로 개인 workspace를 선택하고 체험 자료와 실제 계정 자료를 자동 혼합하지 않는다.
  • 현재 전역 단일 세션을 요청별 연결 관리자로 변경한다. 브라우저에는 무작위 앱 세션 쿠키만 HttpOnly · Secure · SameSite로 보관한다. 서버는 쿠키의 해시·만료와 workspace 연결을 관리하고, 원본 세션 값은 연결 서버 메모리에만 둔다. 서버 재시작·원본 세션 만료 시 외부 연결은 다시 요구하되 Supabase 자료는 보존한다.
  • 원본이 갱신한 세션은 해당 사용자의 연결 안에서만 반영한다. 세션 입력·종료·전환은 다른 사용자의 연결에 영향을 주지 않는다. 소유자의 기존 세션도 같은 개인 연결로 이전한다.
  • Supabase 접근은 서버 Route Handler를 통한다. 개인 테이블과 Storage의 직접 익명 접근은 닫고 서버에서 매 요청 workspace 소유권을 검사한다. Supabase 비밀키는 서버 전용이며 브라우저·GitHub·설치물에 포함하지 않는다. 서비스 키는 RLS를 우회하므로 RLS만으로 서버 요청의 사용자 격리가 보장된다고 간주하지 않는다.
  • 앱 회원가입·별도의 비밀번호 회원 시스템은 만들지 않는다. 기존 원본 연결과 guest workspace로 구성한다. 과제 기본 범위를 넘는 사용자별 분리는 ‘전체 공개·각자 연결’ 요구를 충족하기 위한 추가 구현이다.
  • 공개 환경에서는 종료·전체 로그·원본 리소스 덤프·전역 setup token 조회 등 개발 제어 경로를 노출하지 않는다. 쓰기 요청의 Origin·CSRF 토큰과 요청 크기를 검사하고, 개인 응답은 공유 캐시를 사용하지 않는다.
  • WIF는 기존 프로젝트를 사용하되 초기 동시 생성은 사용자당 1건·서버 전체 2건으로 제한한다. 초과 요청은 대기/재시도 상태로 반환하며, 누가 어떤 작업을 요청했는지 비밀값 없이 기록한다. 외부 발행과 예약은 해당 사용자가 화면에서 명시적으로 실행한 요청만 전달한다.
‘전체 공개’는 전체 화면에 접근할 수 있다는 뜻이다. 다른 사용자의 개인 원고·세션·제휴 자격·계정 쓰기 권한이 공용으로 공유되는 구성이 아니다. 이 기준은 대화에서 사용자가 선택한 ‘모든 화면 공개, 원본 계정은 각자 연결’을 반영한다.

6. 구현 순서·데이터 이전·AWS 배포

단계구현 내용통과 기준
1. 기준선 고정현재 실행 자산·패치·H 로고·화면별 기능·API 계약을 버전 고정한다. 기능표에는 원본/로컬/미검증/현재 계정 비노출을 구분한다.현재 82개 테스트와 기존 화면·메뉴·AI 증거가 재현되고 원본 자료가 보존됨.
2. Next·Supabase 기반web 앱, 서버 환경변수, SQL migration, 테이블·Storage, 서버 검증·오류 형식, 사용자 workspace를 구현한다.합성 데이터로 DB CRUD·파일 업로드와 사용자 A/B 격리 검사 통과.
3. 과제 CRUD 완성원본 벤치마킹의 등록·목록·상세·수정·삭제·페이지 동작을 Supabase에 연결한다. 추가 메뉴나 관리 화면 없이 기존 화면에서 수행한다.원본 UI에서 Storage 파일 포함 전체 흐름이 새로고침·서버 재시작 후에도 유지됨.
4. 전체 기능 통합세 에디터, 원고, 페르소나·양식, 계정 분석, 아카이브, 제휴, 수익, 발행 이력을 순서대로 공통 저장 계층에 연결한다.각 기능의 입력·처리·저장·재열기 확인. 외부 반영과 Supabase 동기화 상태가 일치함.
5. 이전·호환 검증기존 로컬 보관함·폴더·파일을 소유자 workspace로 복사한다. 원본 계정 자료는 원본 ID를 키로 읽기 가져오기를 수행한다.건수·참조·파일 해시 비교. 중복 가져오기 없음. 원본·로컬 자료를 삭제하지 않고 되돌릴 수 있음.
6. AWS 사전 운영Linux runner, HTTPS Origin 처리, 공개 경로, 확장 origin, 업로드·SSE·대기 시간·오류 로그를 검증한다.원본 세션 연결, WIF 생성, 쿠팡 연결 상태, 업로드·재생·사용자 분리 정상.
7. 공개 배포·제출검증된 릴리스를 배포하고 HTTPS에서 CRUD·파일·AI·주요 원본 흐름을 재확인한다. README·QA표·저장소 및 배포 URL을 정리한다.실제 배포 URL에서 미션 6 전체 CRUD가 동작하고 미검증·권한 제한 항목을 구분해 제출.

배포 구성

  • 목표 주소는 https://hongthreads.hongsik.blog로 정한다. 현재 서버가 사용하는 hongsik.blog의 별도 서브도메인에 A 레코드와 인증서를 추가한다. 기존 도메인·WordPress Nginx 설정을 덮어쓰지 않고 독립 vhost를 추가한다.
  • 현재 EC2는 Ubuntu, t3.medium, 약 4GB RAM이며 Nginx·PHP-FPM·MariaDB와 여러 앱이 함께 운영 중이다. 확인 시점 가용 메모리는 약 2.5GB, 디스크 여유는 약 29GB다. Linux CI에서 빌드한 standalone 릴리스를 올리고 EC2에서 무거운 빌드를 병행하지 않는다.
  • Nginx가 80→443 리다이렉트, TLS, 업로드 상한, 요청 제한과 프록시를 담당한다. 공개 요청은 DRT 연결 서버를 통해 원본 화면과 서버 API로 전달한다. 이전 /workspace HTML 주소는 원본 화면으로 이동시킨다. Next.js 자체 호스팅 문서의 역프록시 구성을 따르며 AI 스트리밍 경로는 버퍼링을 끄고 180초 처리 시간에 맞춘다.
  • 현재 서버의 localhost Host 검사와 http://Host Origin 비교를 그대로 배포하지 않는다. PUBLIC_ORIGIN=https://hongthreads.hongsik.blog를 기준으로 검사하고, 신뢰하는 loopback Nginx에서 전달된 헤더만 사용한다. 9250·9251은 외부에 열지 않는다.
  • Next와 연결 서버는 별도 systemd 서비스로 운영한다. 기존 worker는 기존 Node.js 20.20.2 실행 환경을 유지하고, AWS 연결 서버는 Windows의 ssh.exe 대신 해당 worker를 로컬 subprocess로 호출한다. 기존 WIF 설정·worker 파일·WordPress DB는 교체하지 않는다.
  • 배포는 버전별 release 디렉터리와 current 링크로 구성한다. 새 릴리스의 상태 확인과 Nginx 설정 검사를 통과한 뒤 전환한다. 실패 시 직전 실행 릴리스로 되돌리며 Supabase 자료를 지우지 않는다. DB 변경은 이전 코드와 공존 가능한 추가 방식부터 적용한다.

환경·운영 설정

최소 환경변수는 PUBLIC_ORIGIN, SUPABASE_URL, SUPABASE_SECRET_KEY, SESSION_SIGNING_SECRET, INTERNAL_BRIDGE_SECRET, DATA_BACKEND, VERTEX_TRANSPORT, VERTEX_WORKER_PATH, VERTEX_NODE_PATH, VERTEX_PROJECT, VERTEX_LOCATION, VERTEX_MODEL이다. 실제 값은 서버의 접근 제한된 환경 파일/서비스 credential에 넣고 문서에는 이름과 설명만 남긴다.

원본 세션 만료·403·429·원본 버전 불일치·WIF 실패·Storage 실패·DB 동기화 지연을 분리해 기록한다. 로그에는 cookie, 제휴 비밀키, WIF 자격값을 기록하지 않는다. 확장은 localhost 고정 주소에서 선택한 HTTPS 서비스 주소도 사용하도록 변경하며, 사용자별 확장 연결 키로 해당 workspace에만 저장하게 한다.

  • GitHub 전용 저장소: 실행 소스, 잠금 파일, DB migration, 합성 seed, 환경변수 예시, 기능 명세, QA 체크리스트, 배포 절차와 롤백 절차. 평가자가 접근할 수 있도록 공개하거나 접근 권한을 제공한다.

  • README: 서비스 소개, 전체 기능별 저장 위치·외부 의존성, 데이터 관계, 로컬 실행, 환경변수 이름, AWS URL, CRUD·파일 시연 절차, 검증 결과와 제한사항을 포함한다.
  • 제출 링크: GitHub 저장소 URL과 AWS HTTPS 배포 URL. 첨부 미션의 Vercel 항목을 AWS로 대체한다는 요청은 반영하지만, 교육기관의 배포 방식 인정 여부까지 확인된 것으로 쓰지 않는다.
현재 외부 준비: 전용 Supabase 프로젝트·migration·서버 키, GitHub 저장소, DNS A 레코드와 HTTPS가 연결됐다. 사용자 배포 승인 지시 이전의 최초 배포본과 현재 로컬 수정본은 서로 다른 버전이다. 승인 후 수정본을 CI 검사·배포하고 공개 HTTPS에서 최종 QA한다. 기존 로컬 벤치마킹은 확인 당시 폴더·스크랩 모두 0개여서 옮길 사용자 자료가 없었다.

요구사항 근거: 사용자가 첨부한 코드잇 미션 6 화면과 대화의 확정 선택. 구현 근거: 현재 프로젝트·기능 검증 기록 및 EC2 읽기 전용 점검.
